# Bug 修复 Checklist

这份清单确保 Bug 修复过程完整、可追踪，并防止回归。

## 修复前 - 理解问题

- [ ] **阅读 Issue 描述**
  - 理解预期行为 vs 实际行为
  - 确认能复现问题
  - 理解影响范围和严重程度

- [ ] **收集信息**
  - 检查相关日志和错误信息
  - 确认受影响的版本
  - 确认环境信息（Node.js 版本、操作系统、浏览器等）
  - 检查是否有相关或重复的 Issue

- [ ] **复现问题**
  - 在本地环境复现
  - 记录复现步骤
  - 确认最小复现条件
  - 如果无法复现，与报告者沟通获取更多信息

- [ ] **根因分析**
  - 定位问题代码位置
  - 理解为什么会出现这个问题
  - 评估影响范围（是否影响其他功能）
  - 考虑是否有更深层的设计问题

## 修复中 - 实施修复

- [ ] **创建分支**
  - 从 `main` 创建修复分支
  - 分支命名：`fix/issue-{number}-{brief-description}`
  - 例如：`fix/issue-123-message-send-failure`

- [ ] **编写修复代码**
  - 修复核心问题
  - 保持代码风格一致
  - 添加必要的注释说明
  - 避免不相关的重构或格式化

- [ ] **添加测试用例**
  - 添加测试覆盖修复的问题
  - 确保测试能捕获原 Bug（先失败，修复后通过）
  - 添加边界情况测试
  - 更新相关测试（如果需要）

- [ ] **本地验证**
  - 运行所有测试：`npm test`
  - 手动验证修复有效
  - 检查是否引入新问题
  - 验证性能无退化

## 修复后 - 质量保证

- [ ] **代码审查**
  - 自我审查代码变更
  - 检查是否有遗漏
  - 确认没有引入技术债
  - 检查错误处理是否完善

- [ ] **文档更新**
  - 更新 CHANGELOG.md（在 `[Unreleased]` 下的 `Fixed` 部分）
  - 更新相关文档（如果 Bug 暴露了文档问题）
  - 更新配置示例（如果相关）
  - 添加代码注释（如果逻辑复杂）

- [ ] **跨版本检查**（如适用）
  - 确认问题在哪些版本存在
  - 评估是否需要向后移植（backport）
  - 记录版本信息

## 提交 - 版本控制

- [ ] **提交代码**
  - 使用清晰的 commit message
  - 格式：`fix(scope): 简短描述 (#issue-number)`
  - 例如：`fix(composer): 修复消息发送失败问题 (#123)`
  - Commit body 包含：
    - 问题描述
    - 修复方案
    - 影响范围
    - 关闭 Issue：`Closes #123`

- [ ] **推送并创建 PR**
  - 推送分支到远程
  - 创建 Pull Request
  - PR 标题与 commit message 一致
  - PR 描述包含：
    - 关联的 Issue
    - 问题说明
    - 修复方案
    - 测试说明
    - 截图（如适用）

## PR 审查 - 质量把关

- [ ] **自动化检查**
  - CI 测试全部通过
  - 代码格式检查通过
  - 没有引入新的 linting 警告

- [ ] **人工审查**
  - 等待 Code Review
  - 回应审查意见
  - 必要时修改代码
  - 重新测试

## 合并后 - 验证和关闭

- [ ] **合并到主分支**
  - Squash merge（保持历史清晰）
  - 确认 merge commit message 清晰
  - 删除修复分支

- [ ] **发布验证**
  - 在下一个版本中验证
  - 在生产环境验证（如适用）
  - 通知原始报告者

- [ ] **关闭 Issue**
  - 确认问题已解决
  - 添加关闭评论说明修复版本
  - 例如：`已在 v0.6.0 中修复`
  - 关闭 Issue

- [ ] **后续跟进**（如需要）
  - 监控是否有相关问题报告
  - 评估是否需要进一步改进
  - 更新 FAQ（如果是常见问题）

## 特殊情况处理

### 无法复现的 Bug

- [ ] 与报告者沟通获取更多信息
- [ ] 尝试在不同环境复现
- [ ] 添加更多日志以便调试
- [ ] 如果长期无法复现，标记为 `cannot-reproduce` 并暂时关闭

### 需要紧急修复的 Critical Bug

- [ ] 跳过部分流程（如完整测试覆盖）
- [ ] 优先修复核心问题
- [ ] 紧急发布补丁版本
- [ ] 后续补充完整测试

### 涉及多个模块的复杂 Bug

- [ ] 拆分为多个子任务
- [ ] 逐个模块修复和测试
- [ ] 最后进行集成测试
- [ ] 考虑分多个 PR 提交

### 第三方依赖导致的 Bug

- [ ] 确认依赖版本
- [ ] 检查是否有修复版本
- [ ] 评估升级风险
- [ ] 如无修复，考虑临时解决方案或替换依赖
- [ ] 在上游仓库报告问题

## Commit Message 规范

### 格式

```
<type>(<scope>): <subject> (#issue)

<body>

<footer>
```

### Type

- `fix` - Bug 修复
- `feat` - 新功能（通常不在 Bug 修复中使用）
- `docs` - 仅文档更改
- `test` - 添加或修改测试
- `refactor` - 代码重构（不修复 Bug 也不添加功能）
- `perf` - 性能优化
- `chore` - 构建过程或辅助工具的变动

### Scope

- `core` - 核心逻辑
- `transport` - 传输层（HTTP/WebSocket）
- `client` - 客户端代码
- `config` - 配置相关
- `docker` - Docker 相关
- `deps` - 依赖更新

### 示例

```
fix(composer): 修复中文输入法导致的重复发送问题 (#456)

问题：使用中文输入法时，Enter 键会触发两次发送。

修复方案：
- 在 keydown 事件中检查 isComposing 状态
- 忽略 keyCode 229 的事件
- 使用 compositionend 事件确保输入完成

影响范围：所有使用中文输入法的用户

Closes #456
```

## 质量标准

每个 Bug 修复必须满足：

1. ✅ **可验证**：有明确的验证步骤
2. ✅ **有测试**：新增或更新了测试用例
3. ✅ **无副作用**：没有引入新问题
4. ✅ **可追踪**：清晰的 commit 和 PR 记录
5. ✅ **已文档化**：CHANGELOG 已更新

## 常见错误

❌ **只修复表面问题，未解决根本原因**
✅ 深入分析根因，从源头解决

❌ **修复时引入不相关的改动**
✅ 保持修复聚焦，其他改进另开 PR

❌ **没有添加测试用例**
✅ 每个 Bug 修复都应有对应测试

❌ **Commit message 不清晰**
✅ 使用规范的 commit message 格式

❌ **忘记更新 CHANGELOG**
✅ 每次修复都更新 CHANGELOG
