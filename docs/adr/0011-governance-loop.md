# ADR-0011: 基础治理闭环

## Status

已接受（2026-09-22）。随 v1.5 实现，发布前以主分支为准。嵌入、提交前审核和通用 Policy 端口不在本决策里。阶段见 [路线图](../../ROADMAP.md)。

## Context

v1.3 的人员页只能禁言、请离和拉黑 IP，对象是这一席。v1.4 把稳定 `userKey` 放进席位，但没有持久拒绝名单，也不能从历史里撤下已经发出的正文。

产品边界：

- 不建会员目录、注册或申诉工单。
- 不把删除做成消息编辑。
- 临时模式不悄悄获得永久审计库。
- Protocol v4 不升号。
- 提交前词表、模型审核和视觉审核晚于治理和嵌入，本决策不改 ACK 管道。

回复预览在发送时抄进 `replyTo.text`。只改原消息、不处理读路径，引用里还会留下原文。

## Decision

### 墓碑，不硬删

操作者移除内容时保留 `id`、`seq`、作者和 `createdAt`，写入 `removedAt`，并从该行删掉正文、图片、提及、回应和它自己的引用预览。

对外投影是 `{ id, seq?, author, createdAt, removed: true }`。历史分页、加入快照和在线客户端都走这个投影。在线客户端另收 `messageRemoved`；本地如果有引用这条的 `replyTo`，改成 `{ id, removed: true }`。

引用行里已经抄下的预览不回写全表。读出时若原消息已是墓碑，投影丢掉预览正文。磁盘上的旧引用行仍可能留着原文，直到那条引用自己按留存策略消失。这是已知权衡。

已移除的消息不能再被回应或引用，返回 `MESSAGE_REMOVED`。人和 Agent 的公开消息同一条路径。

### 举报不自动隐藏

加入后的人可以发 `report`（可选 200 字说明）。同一席对同一条未处理举报不重复入库。举报不广播，也不改消息。

没有值班台（不是 sqlite，或没有 operator token）时返回 `GOVERNANCE_UNAVAILABLE`。客户端只在 `stateStart.governance === true` 时显示举报。

### 稳定用户拒绝名单

`moderation.userDenyList` 与 `ipDenyList` 同段，最多 64 条，格式与宿主 `sub` 相同。这是拒绝名单，不是用户表。

- Schema v1 可以只写 `userDenyList`，以便内存模式配合宿主身份。`ipDenyList` 仍只属于 Schema v2。
- Schema v2 两份名单都可写。值班台保存任一份时保留另一份，认领整个 `moderation` 段。
- `join` 和其后的命令都检查。命中则 `USER_DENIED`，并以 `4011 / user_denied` 关闭，不降级成访客。
- 名单更新时，在线且 `userKey` 命中的席位按同一关闭码离开。访客和 Agent 席没有 `userKey`，不受这份名单影响。

### 操作记录

禁言、请离、两份名单、忽略举报和移除内容写入 `operator_actions`。只在有值班台时存在，重启仍在，最多保留 200 条。不记录令牌、正文或图片。

## Alternatives

- **硬删除**：历史和引用对不齐，seq 出现空洞。否决。
- **回写每一条引用**：正确但要扫全表。留到真有磁盘清除要求时再做。
- **内存模式也收举报**：没有人能看。否决。
- **把 userKey 拒绝做成用户表**：变成账号系统。否决。
- **提交前审核和这次一起做**：要改同步 ACK 路径，和墓碑不是一件事。否决，排在嵌入之后。

## Consequences

### 好的影响

- 值班的人可以处理「这条不该留着」和「这个稳定用户不能再进」，不必先做嵌入。
- 旧配置不写 `userDenyList` 时行为与 v1.4 相同。

### 坏的影响 / 权衡

- 引用行的库内预览可能仍含原文。对外展示不再含。
- 墓碑不是磁盘级清除。

### 未来工作

- 嵌入预览是下一版，并把浏览器检查改为阻塞发布。
- 同步词表晚于嵌入。第二个消费方出现后再抽 Policy 端口。视觉审核保持可选。
